# SHK Backend Phase 3 Contract: Testimony Module

# Phase 3.1 - Salvation/Life Testimony (one-per-user)

> Backend phase contract for the Salvation/Life Testimony module, following the SHK backend phase template.  
> This is the source of truth for how one-per-user salvation testimonies behave in v1 and how they plug into later Testimony Wall and moderation phases.

---

## A. Phase name, scope, and goals

**Phase ID:** TEST P3.1  
**Short name:** Salvation/Life Testimony (one-per-user)  
**Owner(s):** Hunter (product/requirements), Isaac / future devs (implementation)  
**Target release (v1.0 / later):** v1.0 public launch

**Scope summary (1–3 bullets):**

- Give each user a single, short Salvation/Life testimony they can draft privately and optionally publish on their profile.
- Define how salvation testimonies will later surface in the Testimony Wall (Salvation tab) without over-building the full Wall or prayer system yet.
- Ensure salvation testimonies run through the same safety/moderation concepts as other user content.

**In-scope (P3.1):**

- One-per-user salvation/life testimony concept and UX.
- Private vs public visibility, with private-by-default behavior.
- Unified help/inspiration content, accessible via a `?` panel, with a short inline placeholder when empty.
- Basic integration points for the future Salvation tab on the Testimony Wall (data fields and conceptual “share/update on Wall” behavior), even if the full Wall UI is deferred.
- High-level moderation assumptions (shared with the testimony/prayer system).

**Out-of-scope (deferred to later phases):**

- General “Staff/Testimony” entries with tags and full Testimony Wall feed (P3.2/P3.3).
- Prayer request data model and flows (P4).
- Reactions/Amen, follow/connection, notifications, and full moderation queues (P5 / moderation phases).
- Long-form “full story” testimony, version history, and rich formatting.

## B. Data model

High-level: P3.1 defines the **salvation testimony concept** and its lifecycle; it does not fully freeze the physical table/column design for the entire testimony system. That will be finalized with P3.2 when general testimonies and tags are specified.

### B1. Conceptual model (v1.0)

- One salvation/life testimony **per account**.
- Short, “elevator pitch” style free-text story (1–3 paragraphs, with an enforced maximum length).
- Two visibility states only: `private` vs `public`.
- Status/flow fields conceptually align with the broader testimony system (draft/published, flagged/under-review), but the exact status enum is finalized in the full testimony contract.

**Assumption for future schema (to confirm in P3.2):**

- Salvation testimonies will either:
  - (Preferred) Live in a unified `public.testimonies` table as rows with `type='salvation'` and a “one per author” constraint; or
  - (Fallback) Use a dedicated `public.salvation_testimonies` table with a parallel structure.
- P3.1 only constrains behavior; exact DDL is finalized with P3.2 to avoid double work.

### B2. Tags and metadata

- Salvation testimonies **do not use topic tags** in v1.
- Future enhancement: optional tags or label “chips” (e.g., addiction, family, school) may be added if there is demand; this is explicitly deferred.
- All heavy topic/tagging concepts (healing, financial, family, work/school, etc.) are reserved for general “Staff/Testimony” entries in P3.2/P3.3 and prayer flows in P4.

## C. Supabase client and JS integration

- P3.1 **reuses** the existing global Supabase client and profile identity (`window.SHK_getSupabaseClient` / `window.shkSupabase`); no new client instances or auth flows are introduced.
- Salvation testimony CRUD uses the same front-end pattern as other account-linked data (owner-based access, via `profiles.id`).
- P3.1 adds three salvation-related fields on `public.profiles` (see Implementation Checklist) but does not otherwise change the Phase-1/2 account identity model.
- Service-role/admin access patterns for salvation testimonies will mirror the later general testimony system; details are finalized with P3.2/P5.

## E. RLS and security assumptions

- Salvation testimonies are treated as user-generated content with the same baseline security posture as general testimonies and prayers (Phase 3 overall).
- **Ownership rules:**
  - A user can only create, read, update, and delete their own salvation testimony.
  - Public (guest or other user) reads are allowed only when `salvation_visibility = 'public'` and status is allowed (e.g., not banned/removed).
- **Admin/Mod access:**
  - Admins and moderators (once implemented) may view salvation testimonies for moderation purposes, even when private, consistent with the moderation contracts (Phase 2).
- RLS for the main testimony tables will be finalized in the P3.2 testimony system contract; P3.1 only constrains behavior and visibility to match P2’s moderation assumptions.

## F. UX behavior and edge cases

### F1. Content and length

- Salvation testimony is a **single, short free-text field**, intended as an “elevator pitch” story (1–3 paragraphs).
- There is an **enforced maximum length in the UI** (target ≈ 2000 characters) to keep it readable on profiles and in the future Wall.
- If the story exceeds the visual container, the UI may scroll rather than expanding indefinitely; exact layout is a visual implementation concern.

### F2. Help and placeholder behavior

- There is a `?` help button in the salvation testimony section that opens a collapsible help/inspiration panel below the editor containing:
  1. A top section explaining:
     - What the salvation testimony is for.
     - Guidance on length, tone, and audience (short, clear, Christ-centered, shareable).
     - How to edit, publish/unpublish, and share.
  2. A bottom section with inspiration prompts/questions (used as guidance, not as literal placeholder text).
- When the testimony field is **empty**, the text area shows a short, one-line placeholder (e.g., “Write out how you came to know Jesus…”); the full help/inspiration block is **only** in the `?` panel and remains accessible at all times.
- Once the user starts typing, the placeholder disappears as usual; the `?` panel remains the canonical place for the detailed prompts.

### F3. States and actions

- Conceptual states:

  - **Empty** – no story yet.
  - **Draft (private)** – user has written something, not yet public.
  - **Published (public)** – story is visible on the public profile.
  - **Unpublished** – previously public but toggled back to private.
  - **Flagged/under review** – moderated state; forced private.

- Actions:

  - Create/edit text (in account view).
  - Toggle Private/Public.
  - Copy a shareable link to the public profile (`/u/{handle}/`) via “Share your testimony” (owner) or “Share their testimony” (visitor).
  - Future: explicit “Share/update on Wall” action that will drive Wall activity; this behavior is defined conceptually here but implemented with P3.2/3.3.
  - No full version history; edits overwrite the previous version. Confirmation or messaging around “major edits” can be added later if needed.

### F4. Conceptual Wall behavior (deferred but documented)

- When the explicit “share/update on Wall” action exists (P3.2+):

  - First share:
    - Treat as a Wall activity event for the Salvation tab; `salvation_last_shared_to_wall_at` is set to the current timestamp.
    - UX may show a confirmation (“Share this testimony on the Salvation Wall?”).
  - Subsequent edits:
    - Default behavior: **save quietly** (update the story without posting a new activity).
    - User can explicitly choose “Share/update on Wall” when a change is meaningful; this creates another activity tied to the same underlying story.
- Conceptual behavior for the Wall:

  - Each “share/update on Wall” action is treated as a new activity in the Salvation tab feed (ordered by share time), even though the underlying salvation record is the same.
  - Edits without this action simply change the story for profile display and any future views, but do not generate a new Wall feed item.
- Exact implementation details (activity table vs timestamp-based queries vs explicit “Wall events”) are deferred to P3.2/P3.3. P3.1 only commits to the **user-facing intent** and the existence of `salvation_last_shared_to_wall_at` as a hook.

## G. Testing and QA

P3.1 is considered functionally complete when the following behaviors are verified:

- A new user on `/account/`:

  - Sees the salvation section with short placeholder text and a `?` help button.
  - Can open the help panel and read guidance/prompts.
  - Can write a testimony, leave it **private**, and save successfully.

- Private vs public:

  - When `salvation_visibility = 'private'`, the story appears on `/account/` for the owner only, not on `/u/{handle}/`.
  - When `salvation_visibility` is toggled to `public` and saved, the story appears on `/u/{handle}/` and is no longer shown as private.

- Share buttons and handles:

  - “Share your testimony” on `/account/` and “Share their testimony” on `/u/{handle}/` copy the profile URL when a handle exists.
  - If a user has no handle set, share buttons are hidden or show a clear message that a username is needed before sharing.
  - Share behavior does **not** depend on Wall implementation; it is purely about the profile URL for P3.1.

- Sensitive content preference:

  - The “Hide testimonies that may contain sensitive or heavy content” checkbox on `/account/settings/` correctly updates `show_sensitive` in both `auth.user_metadata` and `public.profiles`.
  - The default for new users is effectively `show_sensitive = true` (checkbox unchecked), matching Phase-2 assumptions.

- Edge cases:

  - Editing a public testimony and switching it back to private hides it from `/u/{handle}/`.
  - Accounts with non-active `account_status` (e.g., suspended/banned) follow whatever constraints are defined in the moderation contracts (likely forced private / hidden on `/u/{handle}/` and Wall).

## I. Operational notes and future TODOs

### I1. Operational notes

- If salvation testimonies are found to be heavily abused or sensitive, admins/mods may temporarily:

  - Force all salvation testimonies to private.
  - Disable any “share/update on Wall” action while keeping the private story feature intact.

- Any migration between separate tables and a unified `public.testimonies` table should preserve:

  - One-per-user constraint.
  - Private/public state.
  - Basic created/updated timestamps and any Wall activity mapping.
