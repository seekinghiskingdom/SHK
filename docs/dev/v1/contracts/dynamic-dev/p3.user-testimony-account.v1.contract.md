# Phase 3.1 - Salvation/Life Testimony (one-per-user)

> Backend phase contract for the Salvation/Life Testimony module, following the SHK backend phase template.
> This will be the source of truth for how one-per-user salvation testimonies behave in v1 and how they plug into later Testimony Wall and moderation phases.

---

## A. Phase name, scope, and goals

**Phase ID:** TEST P3.1
**Short name:** Salvation/Life Testimony (one-per-user)
**Owner(s):** Hunter (product/requirements), Isaac / future devs (implementation)
**Target release (v1.0 / later):** v1.0 public launch

**Scope summary (1–3 bullets):**

* Give each user a single, short Salvation/Life testimony they can draft privately and optionally publish on their profile.
* Define how salvation testimonies surface in the future Testimony Wall (Salvation tab) without over-building the full Wall or prayer system yet.
* Ensure salvation testimonies run through the same safety/moderation concepts as other user content.

**In-scope (P3.1):**

* One-per-user salvation/life testimony concept and UX.
* Private vs public visibility, with private-by-default behavior.
* Unified help/inspiration content, accessible via `?` and as placeholder when empty.
* Basic integration points for the future Salvation tab on the Testimony Wall, including a “share/update on Wall” control.
* High-level moderation assumptions (shared with the testimony/prayer system).

**Out-of-scope (deferred to later phases):**

* General “Staff/Testimony” entries with tags and full Testimony Wall feed (P3.2/P3.3).
* Prayer request data model and flows (P4).
* Reactions/Amen, follow/connection, notifications, and full moderation queues (P5 / moderation phases).
* Long-form “full story” testimony, version history, and rich formatting.

## B. Data model

High-level: P3.1 defines the **salvation testimony concept** and its lifecycle; it does not fully freeze the physical table/column design for the entire testimony system. That will be finalized with P3.2 when general testimonies and tags are specified.

### B1. Conceptual model (v1.0)

* One salvation/life testimony **per account**.
* Short, “elevator pitch” style free-text story (1–3 paragraphs, with an enforced maximum length).
* Two visibility states only: `private` vs `public`.
* Status/flow fields conceptually align with the broader testimony system (draft/published, flagged/under-review), but the exact status enum is finalized in the full testimony contract.

**Assumption for future schema (to confirm in P3.2):**

* Salvation testimonies will either:

  * (Preferred) Live in a unified `public.testimonies` table as rows with `type='salvation'` and a “one per author” constraint; or
  * (Fallback) Use a dedicated `public.salvation_testimonies` table with a parallel structure.
* P3.1 only constrains behavior; exact DDL is finalized with P3.2 to avoid double work.

### B2. Tags and metadata

* Salvation testimonies **do not use topic tags** in v1.
* Future enhancement: optional tags or label “chips” (e.g., addiction, family, school) may be added if there is demand; this is explicitly deferred.
* All heavy topic/tagging concepts (healing, financial, family, work/school, etc.) are reserved for general “Staff/Testimony” entries in P3.2/P3.3 and prayer flows in P4.

## E. RLS and security assumptions

* Salvation testimonies are treated as user-generated content with the same baseline security posture as general testimonies and prayers.
* **Ownership rules:**

  * A user can only create, read, update, and delete their own salvation testimony.
  * Public (guest or other user) reads are allowed only when `visibility='public'` and status is in an allowed state (e.g., `published`, not flagged/removed).
* **Admin/Mod access:**

  * Admins and moderators (once implemented) may view salvation testimonies for moderation purposes, even when private, consistent with the moderation contracts.
* RLS for actual tables is finalized with the P3.2 testimony system contract; P3.1 only constrains behavior and visibility to match P2’s moderation assumptions.

## F. UX behavior and edge cases

### F1. Content and length

* Salvation testimony is a **single, short free-text field**, intended as an “elevator pitch” story (1–3 paragraphs).
* There is an **enforced maximum length** (exact limit to be chosen later, e.g., N characters) to keep it readable on profiles and in the future Wall.
* If the story exceeds the visual container, the UI may scroll rather than expanding indefinitely; details are a visual implementation concern.

### F2. Help and placeholder behavior

* There is a `?` help button in the salvation testimony section that opens:

  1. A top section explaining:

     * What the salvation testimony is for.
     * Guidance on length, tone, and audience (short, clear, Christ-centered, shareable).
     * How to edit, publish/unpublish, and share updates.
  2. A bottom section with inspiration prompts/questions (currently used as placeholder).
* When the testimony field is **empty**, the entire help/inspiration block appears inside the text box as placeholder content.
* As soon as the user types any content, the placeholder disappears from the box but remains **fully accessible** via the `?` help button.

### F3. States and actions

* Conceptual states:

  * **Empty** – no story yet.
  * **Draft (private)** – user has written something, not yet public.
  * **Published (public)** – story is visible on profile and eligible for the Salvation tab.
  * **Unpublished** – previously public but toggled back to private.
  * **Flagged/under review** – moderated state; forced private.
* Actions:

  * Create/edit text (in account view).
  * Toggle Private/Public.
  * Optional explicit “Share/update on Wall” action when saving changes.
  * No full version history; edits overwrite the previous version, with confirmation on “major” edits (e.g., when changing published content).

### F4. “Share/update on Wall” control

* In the salvation edit UI, there is an explicit control (button or toggle) for **whether this save should create/update a visible activity entry on the Salvation tab**:

  * First time moving from *private → public*:

    * Default behavior is to **create a Wall activity entry** automatically.
    * UX may show a confirmation (“Share this testimony on the Salvation Wall?”).
  * Subsequent edits:

    * Default behavior is **save quietly** (update the story without posting a new activity).
    * User can explicitly choose “Share/update on Wall” when they believe the change is meaningful.
* Conceptual behavior for the Wall:

  * Each “share/update on Wall” action is treated as a new activity in the Salvation tab feed (ordered by share time), even though the underlying salvation record is the same.
  * Edits without this action simply change the story in place for profile display and for any future views, but do not generate a new Wall feed item.
* Exact implementation details (activity table vs timestamp-based queries vs explicit “Wall events”) are deferred to the Wall/Feed design in P3.2/P3.3. P3.1 only commits to the **user-facing behavior and intent**.

## G. Testing and QA

* Verify that:

  * A new user can write a salvation testimony, see help content, and save as private.
  * Private testimonies appear only on `/account/` for the owner, never on `/u/{handle}/` or the Wall.
  * Toggling public makes it visible on `/u/{handle}/` and marks it as eligible for Salvation tab queries.
  * The `?` help behavior works as specified (placeholder when empty, panel always available).
  * The “share/update on Wall” control:

    * Triggers an appropriate “Wall update” when expected.
    * Does not create a Wall update when the user chooses not to share.
* Edge cases to cover:

  * Editing a public testimony and **not** sharing to Wall (story updates, feed does not).
  * Editing a public testimony and sharing to Wall (new feed entry appears conceptually).
  * Account with `account_status` not active (e.g., suspended/banned) and how salvation visibility behaves (likely forced private / hidden; see moderation contracts).
  * Flagged/under-review states forcing testimony back to private and communicating that state to the user.

#### 3. Manual QA pass (end-to-end behavior)

5. **Owner flow on `/account/`:**

   * New user, no testimony:

     * Sees help text in the salvation card box, “Write my Testimony!” + “Learn more…” buttons, no status pill, Share-link button hidden.
   * Write + save (Private, Share=No):

     * Moderation passes → testimony saved, pill shows “Private”, no public link, no Wall share; editor closes; view shows saved text.
     * Moderation fails → save blocked, text unchanged, clear alert message shown.
   * Switch to Public, Share=No:

     * Save → pill shows “Public”, Share-link button appears (copying `/u/?handle=...`), public profile shows text, no Wall activity yet.
   * Public + Share=Yes:

     * Save → same as above, plus `salvation_last_shared_to_wall_at` set; confirmation message shows `Visibility: Public / Shared to Wall: Yes`.

6. **Public profile `/u/?handle=...`:**

   * When `salvation_visibility = 'public'` and text non-empty:

     * Header shows name/@handle; main card shows the story; status text indicates “Public salvation testimony” (or similar).
   * When private or empty:

     * Card shows only the neutral line: “This testimony is currently private…”
   * “Share their testimony” copies the URL; “See all testimonies” goes to `/testimony/wall/`; “See my testimony” goes to `/account/`.
