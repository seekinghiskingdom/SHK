## B. Data model

This phase primarily extends the accounts and admin-config data model used by the rest of the system.

### B1. `public.profiles` (canonical app-level account record)

New / confirmed fields (beyond ACC-P1.0 basics like `id`, `display_name`, `handle`, `avatar_key`):

- `role text not null default 'user'`  
  - Values: `'user' | 'mod' | 'admin'`.  
  - Semantics defined in ACC-ROLES v1.0.  
  - `[DONE – column created; wired into header/account/admin gating]`

- `account_status text not null default 'active'`  
  - Values: `'active' | 'suspended_pending_review' | 'suspended' | 'banned_pending_review' | 'banned'`.  
  - For Phase 1.1, this is settable only via admin tools in Supabase/manual intervention; app-level enforcement is intentionally thin.  
  - `[DONE – column created; enforcement beyond “is_banned” style checks deferred]`

- `show_sensitive boolean not null default true`  
  - Per-account preference for whether sensitive content is shown.  
  - Phase 1.1: stored and surfaced on account settings; actual filtering will be added when sensitive flags exist on content.  
  - `[DONE – column created; basic settings UI planned; content wiring [PENDING]]`

- `strike_count integer not null default 0`  
  - Maintains *lifetime* confirmed strike count for the account (per ACC-MOD).  
  - Phase 1.1: stored but not automatically updated anywhere; manual updates only.  
  - `[DONE – column created; automation [PENDING – moderation engine phase]]`

Implementation notes:

- `profiles.role`, `profiles.account_status`, `profiles.show_sensitive`, and `profiles.strike_count` are the **canonical app-level fields**.  
- Mirroring `role` into `auth.users.user_metadata.role` is possible but non-authoritative. `[PENDING – optional sync util if needed later]`

### B2. `public.admin_config` (global moderation/app settings)

Single-row configuration table used by `/admin/settings` and future backend logic.

Initial v1.1 fields:

- `id integer primary key default 1` – phase assumes `id=1` singleton. `[DONE]`  
- `review_all_new_content boolean not null default false` – global “everything goes through a queue” toggle. `[DONE – schema only; not yet used]`  
- `mod_can_final_approve boolean not null default true` – whether mods can finalize approvals. `[DONE – schema only]`  
- `mod_can_final_reject boolean not null default false` – whether mods can finalize rejections. `[DONE – schema only]`  
- `reports_for_auto_hide integer not null default 2` – distinct reporters needed before auto-hide kicks in. `[DONE – schema only]`  
- `strikes_window_days integer not null default 30` `[DONE – schema only]`  
- `strikes_for_short_suspension integer not null default 3` `[DONE – schema only]`  
- `short_suspension_days integer not null default 7` `[DONE – schema only]`  
- `strikes_for_long_suspension integer not null default 6` `[DONE – schema only]`  
- `long_suspension_days integer not null default 49` `[DONE – schema only]`  
- `strikes_for_ban integer not null default 7` `[DONE – schema only]`  
- Additional boolean toggles / numeric limits for rate-limiting and guest-visibility can be added later, but **must** be documented here when used. `[PENDING – future fields]`

Phase 1.1 behavior:

- Table exists with initial row (`id=1`) and sensible defaults. `[DONE – manual seed required once per environment]`  
- Frontend reads this row for admin display only; no live enforcement logic yet. `[PENDING – enforcement logic in Testimony / Moderation phases]`

### B3. `public.admin_action_log` (optional; infra for future moderation logging)

If created during P1.1, the recommended structure is:

- `id uuid primary key default gen_random_uuid()`  
- `admin_id uuid not null references public.profiles(id)`  
- `action text not null` – e.g. `'set_role'`, `'set_account_status'`, `'update_admin_config'`  
- `target_user_id uuid null`  
- `details jsonb null` – structured payload (before/after, reasons).  
- `created_at timestamptz not null default now()`  

Phase 1.1:

- Creating this table is **optional**; recommended if you want early auditing of role/status changes. `[PENDING in prod unless explicitly created]`  
- RLS / access patterns should treat this as admin-only. `[PENDING]`

### B4. Moderation tables (declared, not implemented in this phase)

Per ACC-MOD v1.0, the following tables are **conceptually part of the moderation system** but are *not* created in Phase 1.1:

- `moderation_keywords`  
- `moderation_settings` (superseded here by `admin_config` for core fields)  
- `reports`  
- `moderation_events`  
- `account_penalties`  

Status for Phase 1.1:

- Semantics and fields are defined in ACC-ROLES / ACC-MOD. `[DONE – design-level]`  
- Physical tables, RLS, and UI are **deferred** to the first Testimony/Moderation phase. `[PENDING – Phase TEST P2.x / MOD P2.x]`

## C. Supabase client and JS integration

### C1. Single global Supabase client

Phase 1.1 standardizes on a **single shared client**:

- Global script tag in `default.html` includes `@supabase/supabase-js@2`. `[DONE]`  
- `site.js` defines `window.shkSupabase = window.supabase.createClient(SUPABASE_URL, SUPABASE_KEY)` exactly once. `[DONE]`  
- All other code (account pill, admin tools, settings pages) must re-use `window.shkSupabase` and **never** call `createClient` again. `[DONE – current codebase; keep enforced in reviews]`  

Result: the “Multiple GoTrueClient instances detected” warning is eliminated in normal usage. If it reappears, search for stray `createClient` calls. `[RUNBOOK – see I2]`

### C2. Global avatar registry

`site.js` exposes:

- `window.SHK_PROFILE_AVATARS: { key, src, adminOnly }[]` – numeric avatars `1–123` plus reserved SHK logos (`998`, `999`). `[DONE]`  
- `window.SHK_getAvatarUrlByKey(avatarKey)` helper to resolve keys stored in `profiles.avatar_key`. `[DONE]`  

Used by:

- Header account pill.  
- Account/profile pages (`/account/`, `/u/`).  
- Future admin tooling when changing another user’s avatar. `[PENDING – only basic use now]`

### C3. Header account pill behavior

Implemented in `site.js`:

- Signed-out:

  - Pill shows “Sign in” + ✝ initial, links to `/account/sign-in/`. `[DONE]`

- Signed-in:

  - Uses `supabase.auth.getUser()` to resolve current user.  
  - Looks up `display_name` / email for initial.  
  - If `avatar_key` present, uses `SHK_getAvatarUrlByKey` and hides initial.  
  - Pill links to `/account/`. `[DONE]`

Role awareness:

- Phase 1.1 reads `profiles.role` when available (or user metadata) to decide whether to show admin-only CTA(s) in the account area, *not* in the header. `[DONE – via `/account/` admin CTA; see D2]`

### C4. Admin tools Supabase usage

Admin pages (`/admin/`, `/admin/accounts/`, `/admin/settings/`) follow these rules:

- Use `window.shkSupabase`. `[DONE]`  
- If the client is missing or JS fails, show a clear error banner: “Unable to load admin tools (Supabase not available).” `[DONE – user has seen and fixed path issues]`  
- All protected operations depend on the currently-authenticated user having `role='admin'` (or `role='mod'` where read-only access is allowed). `[DONE – basic gating; [PENDING] refinement post-RLS]`

## D. Pages, routes, and UI entry points

### D1. Public/guest routes

Nothing in Phase 1.1 is *only* for guests, but guests can hit:

- `/account/search/` – “Find accounts” search; guests can search by handle/display name and view public profiles via `/u/{handle}/`. `[DONE – public search; RLS ensures only public fields]`  
- Any `/u/{handle}/` profile routes that exist. `[DONE – see D2]`

### D2. Authenticated user routes

Key routes touched by this phase:

- `/account/` – main account hub.  

  - Shows account summary, profile info, and actions. `[DONE – baseline ACC-P1.0]`  
  - Phase 1.1 adds an **Admin Tools** CTA for users with `role='admin'`, styled similarly to the sign-in/out section and linking to `/admin/`. `[DONE]`

- `/account/settings/` – settings and profile management.  

  - Hosts preferences like `show_sensitive` and basic account data. `[PENDING – UI wiring for show_sensitive, strike_count display, etc.]`

- `/account/search/` – new account search surface.  

  - Input: text query; matches on handle/display name/email (per Supabase query).  
  - Output: list of cards with avatar, display name, handle, short info, and “View profile” CTA linking to `/u/{handle}/`.  
  - Behavior: accessible to all users, including guests; no private fields exposed.  
  - `[DONE – first pass; design refinements & more filters [PENDING]]`

- `/u/{handle}/` (canonical profile URL) and `/u/?handle=…` fallback.  

  - Phase 1.1 confirms `/u/{handle}/` as the canonical pattern, with `/u/?handle=…` still supported for backward compatibility.  
  - These pages pull `profiles` data (avatar, display name, handle, any public bio/testimony once implemented).  
  - `[DONE – routing + handle lookup; content still minimal until Testimony module]`

### D3. Admin / moderator routes

Phase 1.1 admin surfaces:

- `/admin/` – entry dashboard.  

  - Only for `role='admin'` (hard-gated in JS + future RLS).  
  - Shows basic overview and links to `/admin/accounts/` and `/admin/settings/`.  
  - `[DONE – scaffolded; content intentionally simple]`

- `/admin/accounts/` – basic account list/search.  

  - Search by handle/display name/email.  
  - Shows minimal fields: avatar, display name, handle, role, account_status, quick “See profile” link to `/u/{handle}/`.  
  - Does **not** yet allow editing role/status from UI. `[DONE – read-only first pass]`

- `/admin/settings/` – admin configuration view for `admin_config`.  

  - Reads the single-row config and renders current values. `[DONE – read-only]`  
  - Editing/saving fields is either disabled or minimal; full edit flow is deferred. `[PENDING – proper form + update logic]`

Moderation-specific queues (`/admin/moderation/...`) are not part of this phase. `[PENDING – Moderation/Testimony phases]`

### D4. Components and partials

Phase 1.1 touches:

- `default.html` – includes Supabase script, sets `window.SHK_BASEURL`, and includes `site.js`. `[DONE]`  
- `header.html` – header navigation, account pill, new search button linking to `/account/search/`. `[DONE – visually acceptable, but layout refinement [PENDING]]`  
- `site.js` – global Supabase client, avatar registry, account pill logic, admin tooling helpers. `[DONE – v1.1; future tweaks will bump minor tag]`

## E. RLS and security assumptions

Phase 1.1 is intentionally conservative; many things rely on simple policies plus role checks until the moderation engine is online.

### E1. Profiles

- `public.profiles` retains Supabase’s default RLS for row ownership (signed-in users can see self; public read access is controlled via existing policies).  
- For account search (`/account/search/`) and admin tools, queries are limited to safe columns (no email for public search). `[DONE – query-level discipline]`  
- Explicit RLS for “public vs private profile fields” should be formalized alongside Testimony/Community modules. `[PENDING]`

### E2. Admin config and logs

- `public.admin_config` currently has RLS **disabled** to keep phase 1.1 simple; JS gating ensures only admins see/use the values. `[DONE – initial compromise]`  
- Long term, `admin_config` should move behind stricter RLS and/or server-side functions, with anon client having only read access where safe. `[PENDING – after moderation tables exist]`

- If `public.admin_action_log` is created, it must be admin-only readable and non-insertable by anon clients. `[PENDING – table likely not present yet]`

### E3. Future moderation tables

- `reports`, `moderation_events`, and `account_penalties` will be created with strict RLS (no public access; mod/admin/service-role only). `[PENDING]`  
- This phase does not expose any partial or placeholder versions of those tables to avoid migrations later. `[DONE – intentionally deferred]`

## F. UX behavior and edge cases

Key behaviors to be aware of:

- If Supabase fails to load on any admin page, show the “Unable to load admin tools (Supabase not available)” message and do not attempt further calls. `[DONE – implemented]`  
- If `/account/search/` returns no results, show a clear “No accounts found” state rather than a blank area. `[DONE]`  
- If `/u/{handle}/` is requested for a handle that does not exist, render a friendly “Profile not found” message and suggest checking spelling or using account search. `[PENDING – ensure implemented consistently]`  
- When a signed-in user loses `role='admin'` (manually via Supabase for now), the next page load should hide `/admin/` CTAs and block admin pages. `[DONE – gating relies on live role lookup; manual tests recommended after role changes]`

Edge cases still to formalize:

- Behavior when `account_status` is not `'active'` (suspended/banned accounts) – for now, flows are mostly unaffected, but future phases will enforce read-only and hide content. `[PENDING – moderation engine]`  
- What guests vs signed-in users see on profile pages once testimonies and other UGC are attached. `[PENDING – Testimony module]`
